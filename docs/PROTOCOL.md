# 通信プロトコル

iPhone アプリ（サーバ）と Windows 受信アプリ（クライアント）の間の通信仕様です。

- 変更はすべて「追加のみ」です。**未知の種別・未知のキーは、両側とも無視します**（古いアプリとも動くようにするため）。
- 表の「v1.3」「v1.4」はプロトコルの改訂番号で、アプリのバージョンとは一致しないことがあります（v1.3 はアプリ 1.3.0、v1.4 の音声チャンネルはアプリ 1.3.6 で入りました）。
- 「v1.4.0以降」と書いてある項目（セキュリティの認証・録画の追加分）は、アプリ v1.4.0 で入ります。
- **プロトコル v2.0** で、Wi-Fi の認証と暗号化を作り直しました（PIN とコードは廃止）。**v1 の相手とは Wi-Fi ではつながりません**（USB だけは警告つきでつながります）。詳しくは「セキュリティ（v2）」の節を見てください。以前の「認証（v1.4.0以降）」「ペアリング要求（v1.6）」の節は、v1 の説明として最後に残してあります。

## 接続

| ポート | 用途 |
|---|---|
| 5555 | メインの接続（映像・状態・制御・ping） |
| 5556 | 音声専用チャンネル（プロトコル v1.4） |

- iPhone は TCP サーバとして待ち受けます。
- USB: Apple Mobile Device Service（usbmux）経由で、同じデバイス ID に対してポートごとに Connect します。
- Wi-Fi: iPhone の画面に表示される IP アドレスへ直接 TCP 接続します。
- TCP_NODELAY を使います。

### Wi-Fi の検出と QR ペアリング

- Wi-Fi 接続の許可中、iPhone は Bonjour の `_phonecam._tcp` をポート 5555 で公開します。TXT の `id` はインストールごとの UUID、`name` は利用者が設定した端末名（未設定なら機種名。UTF-8 で 63 バイト以内）、`model` は機種名（例: `iPhone 13`。63 バイト以内）、`v` は検出・ペアリング手順の版（現在は `2`。`1` も候補として読みます）です。**Bonjour は候補の一覧にだけ使います。** 鍵は公開しないので、見つかっただけでは接続先として信頼しません（接続時にピン留めした鍵で確かめます）。
- PC が表示する `phonecam://pair` URI のクエリは `ips`（カンマ区切りの IPv4 候補。待ち受けはこのアドレスだけに開きます）、`port`、`token`、`name`、`v`（`2`）、`fp`（PC の静的公開鍵の指紋）です。待ち受けは表示中だけ有効で、トークンは 180 秒で失効するか、1 回成功した時点で消費されます。同じ送信元からの接続は 1 本までです。
- 手順は「セキュリティ（v2）」の「QR ペアリング」を見てください。PIN やコードは送りません。
- PC は相手の公開鍵・指紋・名前だけをローカル設定に保存します（PIN は保存しません）。映像・音声は既存のポートと、v2 のハンドシェイクを使います。

- 状態 JSON（status）にも `device_name`（端末名）と `model`（機種名）を含めます。

### 複数端末の識別

- iPhone の認証後の状態 JSON に、Bonjour と QR と同じインストール UUID が `deviceId` として入ります。
- USB のときだけ、usbmux 経由のループバック TCP ポート 5557 から同じ UUID を ASCII 36 バイトと改行で取得できます。読み取り専用です。映像接続を開かずに USB と Wi-Fi の接続先が同一端末かを判定します。
- 旧版 iPhone では 5557 が開きません。USB で最初につないだプロファイルは usbmux のシリアル番号を保存して再接続できます。

## フレーミング

TCP 上のメッセージは `[種別 1byte][長さ 4byte ビッグエンディアン][本体]` です。

| 種別 | 方向 | 内容 |
|---|---|---|
| 1 | iPhone → PC | H.264 アクセスユニット |
| 2 | iPhone → PC | HEVC アクセスユニット（Annex B。キーフレームには VPS/SPS/PPS を付加） |
| 3 | iPhone → PC | 状態 JSON |
| 4 | iPhone → PC | pong（JSON） |
| 5 | iPhone → PC | 映像1枚ごとの時刻情報（16byte、次の映像パケットの直前に送る） |
| 6 | iPhone → PC | マイク音声 |
| 10 | PC → iPhone | 制御 JSON |
| 20 | 両方向 | v2: 暗号化された 1 メッセージ（Wi-Fi の認証後は、すべてこの種別で包みます） |

- PC 側はデコーダーを1つだけ保持し、受信した種別のコーデックが現在と違えばデコーダーを作り直し、キーフレームを要求します。

## iPhone → PC のパケット


### ビットレートの自動調整（Wi-Fi）

- PC → iPhone の制御 JSON に `"adaptiveBitrate": true|false` を追加します。PC は接続ごとに現在の経路に合わせて送り、USB では常に `false` です。iPhone も USB ではこの指定を無視します。指定がない接続では固定ビットレートのままです。
- 従来の `"bitrate"`（Mbps）は、自動調整中は上限になります。送信待ちバイト数・最も古い送信待ち・送信完了までの時間・破棄数を毎秒計測し、混雑時に下限（上限の約30%）まで段階的に下げます。映像の送信が8秒連続で安定したら少し戻します。解像度と fps は変更しません。
- iPhone → PC の状態 JSON は `bitrateTargetMbps`（エンコーダーの目標値）、`bitrateSentMbps`（Wi-Fi で送信処理が完了した映像ペイロードの Mbps）、`adaptiveBitrateEnabled`（有効か）、`adaptiveBitrateReduced`（目標値が上限より低いか）を返します。計測値は Wi-Fi 配信中のみです。送信完了は iPhone の TCP 送信処理で計測し、PC の受信完了を表すものではありません。
- 接続が切り替わると混雑の履歴をリセットします。旧版では未知のキーを無視できます。

### 種別 4: pong（JSON）

`{"pong": <PCが送ったpingの値>, "t": <iPhoneのホスト時計[秒]>}`

ping を受け取ったらすぐに返します（キューに溜まった映像より先に送ります。状態と同じ優先度で、捨てません）。

### 種別 5: 映像の時刻情報（16byte）

`float64 BE captureTime` + `float64 BE sendTime`

- iPhone のホスト時計[秒]です。ホスト時計は `CMClockGetTime(CMClockGetHostTimeClock())` で、`captureTime` はカメラのサンプルバッファの PTS（`CMTimeGetSeconds`）、`sendTime` は映像パケットをネットワークへ渡した時刻です。
- 実際に送る映像パケットの直前に、同じキューで送ります（順序が保証されます）。捨てたフレームには付きません。

### 種別 6: マイク音声

`float64 BE captureTime`（最初のサンプルの時刻） + `uint32 BE sampleRate` + `uint8 channels`（常に 1。iPhone がモノラルにします） + `int16 リトルエンディアン PCM`

- 取得したバッファをそのまま送ります（通常は約 20ms。低遅延経路では約 5ms）。
- 映像の間引きロジックでは捨てません。ただし送信キューに溜まった音声が上限を超えたら、止まらずに古い方を捨てます（メイン 5555 では約 200ms、音声チャンネル 5556 では約 60ms）。

### 種別 3: 状態 JSON

基本のキー: `codec`, `background`, `color`, `thermalState`（`nominal`/`fair`/`serious`/`critical`）, `batteryLevel`（0〜1、不明は -1）, `batteryState`（`charging`/`full`/`unplugged`/`unknown`）, `lowPowerMode`（bool）, `processingMs`（float）

| 追加された版 | キー |
|---|---|
| v1.3 | `pressureLevel`（`nominal`/`fair`/`serious`/`critical`/`shutdown`。アクティブなカメラの `systemPressureState.level`）, `pressureFactors`（`systemTemperature`/`peakPower`/`depthModuleTemperature`/`cameraTemperature` の配列）, `sentFps`, `cameraDroppedFrames`（接続してからの数）, `networkDroppedFrames`（同）, `encodeMs`（移動平均）, `screenBlack`, `autoBlackSeconds`, `mic`（`{enabled, available, sampleRate}`）, `recording`（`{active, seconds, fileName, bytes, freeBytes, resolution, error}`。エラーが無いときの `error` は空文字）, `recordSettings`（現在値の返信） |
| v1.4 | `streamActive`（iPhone が持っている現在値）, `cameraRunning`（`AVCaptureSession.isRunning`。カメラが実際に動いているか）, `audioChannel`（音声チャンネルが繋がっているか）, `micPath`（iPhone のマイク経路。`lowLatency` = 低遅延エンジン経路、`capture` = 通常のキャプチャ経路） |
| v1.4.0以降 | `wifiAllowed`（Wi-Fi 接続を許可しているか）, `authRequired` / `authOk`（認証。下記）, `recording.droppedFrames`, `cameraDropReasons`（`{"late": n, "outOfBuffers": n, "discontinuity": n}`） |

- `streamActive` と `cameraRunning` は、どちらかが変わったときにすぐ状態を送ります。カメラが止まっている間は、露出や ISO などカメラ由来の値が古いままのことがあり、映像・時刻情報のパケットも来ません。

## PC → iPhone の制御（種別 10, JSON）

| キー | 内容 | 追加された版 |
|---|---|---|
| `"codec"` | `"h264"` / `"hevc"` | 基本 |
| `"background"` | `{"mode": "off"\|"blur"\|"green", "strength": 0〜1（既定0.6）, "quality": "fast"\|"balanced"}` | 基本 |
| `"color"` | `{"brightness": -0.5〜0.5（0）, "contrast": 0.5〜1.5（1）, "saturation": 0〜2（1）, "sharpness": 0〜1（0）}` | 基本 |
| `"ping"` | 数値（PC が決める値。例: perf_counter のミリ秒）。そのまま pong で返ります | v1.3 |
| `"mic"` | `{"enabled": bool}`（既定 false）。オンにすると iPhone が既定の音声入力をセッションに加えます。音声は、クライアントが繋がっている間だけ送ります | v1.3 |
| `"screen"` | `{"black": bool, "autoBlackSeconds": 0\|10\|30\|60}`（省電力） | v1.3 |
| `"recordSettings"` | 録画の設定（下記）。ほかの設定と同じようにマージして保存されます | v1.3 |
| `"record"` | `"start"` / `"stop"` | v1.3 |
| `"stream"` | `{"active": bool}`（下記） | v1.4 |
| `"auth"` | `{"code": "123456"}`（下記） | v1.4.0以降 |

### recordSettings

`{"resolution": "same"|"4k", "bitrate": 10〜100（Mbps、既定50）, "includeAudio": bool（既定true）, "saveToPhotos": bool（既定true）}`

v1.4.0以降 の追加:

- `"preset"`: `"standard"` / `"high"` / `"max"`（既定 `standard`）
- `"container"`: `"mp4"` / `"mov"`（既定 `mp4`）
- `"bitrate"` が無いときは、iPhone がプリセットからビットレートを決めます（HEVC）。

| プリセット | 1080p | 4K |
|---|---|---|
| standard | 10 Mbps | 25 Mbps |
| high | 16 Mbps | 40 Mbps |
| max | 25 Mbps | 60 Mbps |

- 明示的な `"bitrate"` があれば、そちらが優先されます。

### stream（カメラを動かすタイミング）

使っていないときに iPhone のカメラを止めて、発熱とバッテリー消費を抑えるための仕組みです。

- `false` のとき、iPhone はエンコードを止め（エンコーダーを破棄）、録画中・iPhone 側のプレビュー表示中でなければカメラ（マイクも）を止めます。TCP 接続・状態（1 秒ごと）・ping/pong は続きます。
- **既定は true**: 値は接続ごとにしか保持されません。新しいクライアントが繋がるたびに iPhone は `streamActive` を true として扱うので、"stream" を送らない古い PC アプリは従来どおり動きます。新しい PC アプリは、接続直後（"all" の制御に含めて）に希望の値を送ります。
- `true` になったとき、iPhone はキーフレームを要求し、IDR（パラメータセット付き）を送るまでフレームを捨てます。再開後の最初の映像パケットは必ずキーフレームです。
- 映像・音声は `接続中 && streamActive` の間だけ送ります（音声はさらに mic が有効なとき）。
- カメラが動くのは、`(接続中 && streamActive) || 録画中 || iPhone 側のプレビューがオン` のときです。停止中に録画を始めると、カメラは自動で動き始めます。

## 音声チャンネル（ポート 5556、v1.4）

映像と同じ通信路だと、大きな映像のうしろで音が待たされて遅れます。そのため音声は別の接続で送ります。

- iPhone はポート **5556** でも待ち受けます（フレーミングは同じ）。PC は、5555 に繋いだ直後に、USB なら同じデバイス ID で usbmux の Connect（ポート 5556）、Wi-Fi なら直接 TCP で 5556 に繋ぎます（TCP_NODELAY、SO_RCVBUF 64KB）。
- 音声チャンネルとメインの接続が**両方**あるとき、iPhone は種別 6 を**音声チャンネルだけ**で送ります。音声チャンネルが無いときは従来どおり 5555 で送るので、古い iPhone アプリ・古い PC アプリとも互換です（PC は両方の経路の種別 6 を処理します）。
- v2: PC は 5556 につないだら、最初に映像のセッションの `audio_tok` を送ります（「セキュリティ（v2）」の「音声チャンネル」）。v1 のときは何も送りません（任意で、種別 10 の `{"hello": "audio"}`。iPhone は無視してかまいません）。
- iPhone は音声クライアントを 1 つだけ受け付けます（新しい接続が古い接続を置き換えます）。メインの接続が閉じたら音声チャンネルも閉じます。PC は、音声チャンネルが繋がらなければ 2 秒ごとに繋ぎ直します。
- 音声チャンネルのソケットは TCP_NODELAY で、iPhone は未送信の音声を約 60ms までしか溜めません（それを超えたら新しい方を捨てます）。

## セキュリティ（v2）

プロトコル v2.0 の Wi-Fi の認証と暗号化です。部品は **X25519・HKDF-SHA256・ChaCha20-Poly1305** だけです（iPhone は CryptoKit、Windows は `cryptography`）。計算は共有のテストベクタ [test-vectors/handshake-v2.json](test-vectors/handshake-v2.json) で、Windows（pytest）と iPhone（Swift の `HandshakeChecks`）の両方から確かめています。

### 長期鍵とピン留め

- 端末ごとに X25519 の静的鍵を 1 つ持ちます。iPhone は Keychain（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`）、Windows は DPAPI（ユーザー単位）で包んで設定に保存します。
- **指紋** = `base32(SHA256(公開鍵)[:16])`（パディングなし、26 文字）。
- ペアリングで、お互いの公開鍵を相手に**ピン留め**します。次からの接続は、ピン留めした鍵と合うときだけ成立します。合わなければ切断して「再ペアリングしてください」と出します。

### ハンドシェイクのメッセージ

どれも種別 10 の JSON `{"hs": {...}}` です。鍵・nonce・MAC は小文字の 16 進。**トランスクリプト `th` は、送受信した JSON の本体のバイト列そのものを順に連結して SHA-256 した値**です（正規化はしません）。エラーは `{"hs":{"err":"<unpaired|locked|busy|limited|declined|unavailable|version|auth|bad>"}}` を平文で返して切ります。

認証前の 1 メッセージは **64 KiB** まで。ハンドシェイクは接続から **10 秒**で期限切れです。

### 通常の接続（ピン留め済み）

1. PC → iPhone `c1`: `{"hs":{"v":2,"mode":"connect","e":<PC の一時公開鍵>,"n":<乱数 16 バイト>,"sf":<PC の指紋>}}`
2. iPhone → PC `c2`: `{"hs":{"e":<一時公開鍵>,"n":<乱数>,"tf":<iPhone の指紋>}}`。`sf` の鍵を覚えていなければ `{"hs":{"err":"unpaired"}}`。PC は `tf` で、保存済みの iPhone の鍵を引きます（無ければ `unpaired`）。
3. `ikm = DH(e_pc, e_ph) ‖ DH(s_pc, e_ph) ‖ DH(e_pc, s_ph)`、`th = SHA256(c1 ‖ c2)`。`HKDF(ikm, salt=th, info="phonecam v2 session")` の 192 バイトを次に割り当てます。

| 範囲 | 名前 |
|---|---|
| 0–32 | `k_pc2ph`（PC → iPhone の鍵） |
| 32–64 | `k_ph2pc` |
| 64–80 | `audio_tok`（音声チャンネルのトークン） |
| 80–84 / 84–88 | nonce の固定部 `iv_pc2ph` / `iv_ph2pc` |
| 88–120 | `k_confirm` |
| 120–152 / 152–184 | 音声チャンネルの鍵 `ka_pc2ph` / `ka_ph2pc` |
| 184–188 / 188–192 | 音声チャンネルの nonce 固定部 |

4. PC → iPhone `c3`: `{"hs":{"confirm":HMAC(k_confirm,"pc"‖th)}}`。合わなければ `err: auth`（失敗として数えます）。
5. iPhone → PC: `{"hs":{"confirm":HMAC(k_confirm,"ph"‖th)}}`。ここで相互認証が成立します。

### 暗号化（Wi-Fi）

- 認証後の Wi-Fi は、**すべての**メッセージを `[20][長さ][AEAD(種別 1 バイト ‖ 本体)]` で包みます。鍵は方向ごと、nonce は `固定 4 バイト ‖ 方向別 64bit カウンタ（ビッグエンディアン）`、AAD は外側の 5 バイトの見出しです。
- 受け取る側は自分のカウンタでしか復号しないので、**改ざん・順番の入れ替え・欠落・再送はすべて検証に失敗し、切断します**。種別 20 でないメッセージ（平文）が届いたときも切断します。**Wi-Fi の平文は禁止**です。
- 復号後の本体の上限は、これまでの上限（映像 16 MiB、音声 256 KiB）のままです。
- **USB（ループバック）** は同じハンドシェイクで認証だけして、**平文のまま**です（鍵は作りますが通信路には使いません）。
- 認証が済むまで PC は設定・制御・メディアを送らず、受け取った映像もデコーダーに渡しません。

### コード方式のペアリング（PC が始める）

鍵を後から決められないように、PC は先に一時公開鍵の「約束（commit）」を出します。

1. PC → iPhone `m1`: `{"hs":{"v":2,"mode":"pair","commit":SHA256(e_pc‖n_pc),"name":<PC 名>}}`
2. iPhone → PC `m2`: `{"hs":{"e":<一時公開鍵>,"n":<乱数>}}`
3. PC → iPhone `m3`: `{"hs":{"e":<一時公開鍵>,"n":<乱数>}}`。iPhone は `commit` を確かめます（違えば拒否）。
4. 両側で `ss = DH(e_pc, e_ph)`、`th = SHA256(m1‖m2‖m3)`、`code = (HKDF(ss, salt=th, info="phonecam pair sas") の先頭 4 バイト（ビッグエンディアン）) mod 1,000,000` を 6 桁で、`k = HKDF(ss, th, "phonecam pair key")`（32 バイト）を計算します。iPhone は**コードを画面に出します（ネットワークには流しません）**。アプリが前面にあるときは `{"hs":{"ui":"shown"}}`、そうでなければ `{"hs":{"ui":"background"}}` を PC に返します。
5. 利用者が PC にコードを入力します。**合ったときだけ** PC が `{"hs":{"confirm":HMAC(k,"pc"‖th)}}` を送り、続けて AEAD(k)（nonce の固定部は PC → iPhone が `c2p\0`、iPhone → PC が `p2c\0`）で `{"s":<PC の静的公開鍵>,"name","id":<PC の UUID>}` を送ります。合わなければ `{"hs":{"abort":"mismatch"}}`（失敗として数えます）。やめたときは `{"hs":{"abort":"cancel"}}`。
6. iPhone は confirm を確かめ、AEAD で `{"s":<静的公開鍵>,"name","id","model","addresses"}` を返します。**お互いの公開鍵をピン留め**して終わりです（接続は閉じます。続けて通常の接続をします）。

- コードは**使い捨て**です（1 回の試行ごとに作り直し）。入力違いは、同じ IP のロックアウト（3 回失敗で 60 秒）に数えます。
- iPhone は、ポップアップを常に 1 つだけにし、同じ IP からの要求を 10 秒に 1 回に制限し（`limited`）、別の IP の要求中は `busy` を返します。ポップアップは 120 秒で閉じ、「拒否」を押すと `err: declined` を返します。PC 名は表示用に制御文字などを除いて 40 文字までに切ります。
- USB（ループバック）の初回接続は、コードの入力なしで同じ手順を進めます（USB 接続は「このコンピュータを信頼」で守られているため）。

### QR ペアリング

QR は PC の静的公開鍵の指紋（`fp`）・1 回限りのトークン・接続先・PC 名を運びます（鍵そのものや PIN は入れません）。

1. iPhone → PC `q1`: `{"hs":{"v":2,"mode":"qr","e":<一時公開鍵>,"n":<乱数>}}`
2. PC → iPhone `q2`: `{"hs":{"e":,"n":,"s":<PC の静的公開鍵>}}`。**iPhone は `s` の指紋が QR の `fp` と同じときだけ**進み、違えば何も渡さずに切ります。
3. `ikm = DH(e_ph, e_pc) ‖ DH(e_ph, s_pc)`、`th = SHA256(q1‖q2)`、`HKDF(ikm, th, info="phonecam v2 qr")` から通常の接続と同じ割り当てで鍵を作ります。PC → iPhone `q3` = `{"hs":{"confirm":HMAC(k_confirm,"pc"‖th)}}`。
4. iPhone → PC（暗号化）: `{"hs":{"s":<静的公開鍵>,"tok":<QR のトークン>,"name","id","model","addresses"}}`。PC はトークンを確かめ、PC → iPhone（暗号化）`{"hs":{"ok":true,"name","id"}}` を返します。両方が相手の鍵をピン留めします。
- PC の待ち受けは QR に出したアドレスだけに開き、同じ送信元の接続は 1 本まで、トークンは 1 回で失効します。

### 音声チャンネル

- メインのハンドシェイクで作った `audio_tok` が、音声チャンネルと映像のセッションを結び付けます。PC は 5556 につないだら、最初に `{"hs":{"audio_tok":<16 進>}}` を送ります。Wi-Fi ではこのメッセージも**音声用の鍵**（`ka_*`、`iva_*`）で包みます（盗聴した人がトークンを使い回せないように）。USB は平文です。
- iPhone は、メインの認証済み接続と同じ IP で、トークンが合う接続だけを受けます。メインのセッションが変わる（再接続・切断）たびに、古い音声の接続は閉じます。
- v1 の PC との USB だけは、トークンなしでも音声を受けます（警告つき）。

### iPhone の接続の制限

- 認証前の接続は、**同じ送信元から 1 本、全部で 4 本まで**です。期限切れのものは掃除します。
- ロックアウト（同じ IP の確認の失敗・コードの入力違いが 3 回）が始まったら、その IP の認証前の接続も、すでに認証済みの接続も切ります。

### 互換

- v1 の PC（`hs` を知らず、PIN を送る）が Wi-Fi でつなぐと、iPhone は `{"hs":{"err":"version"}}` を返して切ります。PC は v1 の iPhone を、最初のメッセージが `hs` でないことで見分けて Wi-Fi をつなぎません。どちらも「PC と iPhone の両方を最新版にしてください」と表示します。
- USB は v1 の相手とも平文でつながります（画面に警告を出します）。
- v1 で登録した iPhone は、鍵がないので「再ペアリングが必要」と表示します。

## 認証（v1.4.0以降。v1 の説明）

> **v2.0 で置き換えました。** 下は v1（PIN とペアリング要求）の仕様で、v1 の相手との互換を説明するために残しています。

接続の許可についての仕様です。

### USB と Wi-Fi の区別

usbmux 経由の接続は、iPhone から見るとループバックアドレス（127.0.0.1 / ::1）から来た接続として見えます。**ループバックのクライアントは信頼します**（USB 接続には、iPhone 側で「このコンピュータを信頼」が必要なため）。

### Wi-Fi

- Wi-Fi の待ち受けは**既定でオフ**です。iPhone アプリの「Wi-Fiからの接続を許可」で切り替えます（設定は保存されます）。オフのとき、ループバック以外の接続はすぐに閉じます。
- Wi-Fi を許可しているとき、ループバック以外のクライアントは最初に認証します。iPhone は **6 桁のペアリングコード**（ランダム。UserDefaults に保存。「コードを変更」ボタンで変更）を表示します。
- クライアントは、**5 秒以内**に、最初の種別 10 メッセージとして `{"auth": {"code": "123456"}}` を送ります。
- 認証が済むまで、iPhone は状態を 1 つ（`{"authRequired": true, "authOk": false}`）だけ送り、ほかの制御はすべて無視します。映像・音声・時刻情報・pong も送りません。
- コードが違う、または時間切れのときは接続を閉じます。同じ IP から **3 回**失敗すると、その IP を **60 秒間**拒否します。
- 成功すると、通常の状態（`"authOk": true`）を送ります。
- ループバックのクライアントが `{"auth": ...}` を送ってきても無視します（常に OK）。
- 音声チャンネル（5556）は、ループバックからの接続か、現在認証済みのメイン接続と同じ IP からの接続だけ受け付け、それ以外は閉じます。

### ペアリング要求（プロトコル v1.6、Wi-Fi。v1 の説明）

未登録の iPhone につなぐとき、PC は iPhone の画面にペアリングコードをポップアップで出してもらえます（Bluetooth のペアリングと同じ流れ）。iPhone の設定画面でコードを見る方法も、今までどおり使えます。

- **コードそのものはネットワークに流れません。** 送るのは PC の名前と、一回限りの要求 ID だけです。要求が受け付けられても認証は通りません（コードの照合は上の認証のままです）。
- PC は、認証用の接続とは**別の接続**をポート 5555 に開き、iPhone が最初に送る認証前のステータスを読みます。そこに `"pairPopup": 1` があれば、対応しています。**無ければ何も送りません**（古い iPhone アプリには、認証を失敗として数えさせないため）。
- PC → iPhone（種別 10、認証前に送れるのは `auth` とこの 2 つだけ）:
  - `{"pairRequest": {"v": 1, "id": "<英数字と - _ の 8〜64 文字>", "name": "<PC 名>"}}`
  - `{"pairCancel": {"id": "<要求 ID>"}}`（ポップアップを閉じてもらう）
- iPhone → PC（種別 3 のステータス）: `{"pairReply": {"id": "<要求 ID>", "state": "<下の値>"}}`

| state | 意味 | PC の動き |
|---|---|---|
| `shown` | 画面にコードを出した | 「iPhone の画面にコードが表示されています」と出す |
| `declined` | 利用者が「拒否」を押した | ダイアログを閉じて知らせる |
| `background` | アプリが前面にない（ポップアップも通知も出さない） | 「iPhone で PhoneCam を開いて確認してください」と出す |
| `busy` / `limited` / `unavailable` / 未知の値 | 別の PC の要求中 / 回数制限 / 出せない | 今までどおり「iPhone の設定画面でコードを確認してください」と出す |

- 返事が 3 秒以内に来ない、接続が切れる、ステータスに `pairPopup` が無い、のいずれでも、PC は今までどおりの案内に戻します。
- iPhone の規則:
  - ポップアップは 1 つだけです。別の IP の要求が出ている間は `busy`、同じ IP の新しい要求は古いものを置き換えます。
  - 同じ IP からの要求は **10 秒に 1 回まで**です（超えると `limited`）。1 つの接続では要求は 1 回だけです。
  - 認証前の接続は、1 メッセージの本体が **1 KB** を超えると、認証の失敗として数えて切ります。要求だけの接続は、認証の失敗として数えません。
  - 要求を受けたあとの接続は **120 秒**で閉じます。閉じるとポップアップも消えます。要求した PC が接続を閉じる・`pairCancel`・認証の成功（どの接続でも）・アプリが前面でなくなる、でもポップアップを消します。
  - PC 名は表示するだけです。制御文字・書式文字（向きを変える文字など）・行区切りを除き、40 文字までに切り詰めます。
  - Wi-Fi の許可がオフ、またはロックアウト中の IP は、これまでどおり接続ごと拒否します（要求も届きません）。要求は LAN 内の、Wi-Fi の受け付けと同じ範囲の相手だけが送れます。
- 古い PC アプリはこの要求を送りません。古い iPhone アプリは `pairRequest` / `pairCancel` を知らない種別として無視します（`auth` 以外を無視する今までの動き）。

### PC 側の動き

Wi-Fi モードには「ペアリングコード」欄があります（保存されます）。接続した直後（"all" の制御より前）に auth メッセージを送ります。iPhone が `authRequired` かつ `!authOk` と返したり、接続を閉じたりしたら、「ペアリングコードが違います。iPhoneの画面に表示されている6桁のコードを入力してください」と表示します。

> v1 の認証は「同じネットワーク上の知らない人が勝手に繋がらないようにする」ためのもので、通信は暗号化されませんでした。v2 では暗号化されます。詳しくは [SECURITY.md](../SECURITY.md)。

## 遅延の計算

- PC は 1 秒ごとに `ping` を `perf_counter` のミリ秒で送ります。
- 時計のずれ: `offset = iPhone時刻 - (PC送信時刻 + RTT/2)`（直近 15 回のうち RTT が最小のもの）
- `iPhone処理 = sendTime - captureTime`
- `通信 = (PC受信時刻 + offset) - sendTime`
- `PC処理 = 仮想カメラへ渡し終わった時刻 - PC受信時刻`
- 合計 = 3 つの合計。カメラの露光や OBS の表示までの時間は含みません。

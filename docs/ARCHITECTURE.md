# しくみ（アーキテクチャ）

PhoneCam 全体の流れと、低遅延のための工夫をまとめた資料です。通信の細かい仕様は [PROTOCOL.md](PROTOCOL.md) を見てください。

## 全体像

```
iPhone (PhoneCam アプリ)                         Windows PC
 カメラ → 背景・色調整 → H.264/HEVC エンコード ── USB (usbmux) / Wi-Fi ──→  受信アプリ → デコード → 仮想カメラ → OBS / Discord
                                    ←──────  露出・WB・フォーカス等の制御 ──────
```

- iPhone 側は TCP サーバ（ポート 5555。音声用に 5556）として待ち受けます。
- USB 接続では、Apple Devices アプリ（または iTunes）が入れる「Apple Mobile Device Service」（usbmux）を経由して接続します（専用ドライバー不要）。
- Wi-Fi 接続では、iPhone の画面に表示される IP アドレスへ直接接続します。
- 映像は H.264 または HEVC(H.265) のまま送られ、PC 側でデコードして仮想カメラに流します。
- 露出・ホワイトバランス・フォーカス・ズーム・ライト・背景エフェクト・色調整は PC の画面から操作します。
- レンズは「広角」「超広角」「インカメ」から選べます。iPhone 13 のインカメはピント固定（オートフォーカスなし）で、ライトも使えません。インカメの映像は反転せずに送られ、「左右反転」の設定はインカメ用に別で記憶されます（初期値はオン）。

## iPhone 側のパイプライン

ソースは `ios/PhoneCam/` にあります。

1. **カメラ**（`CameraController.swift`）: AVCaptureSession。手ブレ補正オフ、遅れたフレームは破棄。レンズ・露出・WB・フォーカス・ズーム・ライトを PC からの制御で変更。
2. **エフェクト**（`Effects.swift`）: 背景（オフ / ぼかし / 切り抜き(緑)）と色調整（明るさ・コントラスト・彩度・シャープネス）。処理は iPhone 側で行います。
3. **エンコード**（`H264Encoder.swift`）: VideoToolbox による H.264 / HEVC。低遅延レート制御、B フレームなし。HEVC のキーフレームには VPS/SPS/PPS を付加（Annex B）。
4. **送信**（`StreamServer.swift`）: TCP_NODELAY。送信が詰まったときは、キーフレーム以外を破棄します。未送信の映像は最大 1 フレームまで（直前のフレームが未送信なら、キーフレーム以外は捨てる）。
5. **録画**（`Recorder.swift`）: 配信とは別に、iPhone の中で高画質に録画（HEVC）。
6. **マイク**（`LowLatencyMic.swift`）: AVAudioEngine（約 5ms ごと）で取得する低遅延経路。録画で音声を使う間は従来のキャプチャ経路。
7. **状態**: 温度・バッテリー・低電力モード・エフェクト処理時間などを 1 秒ごとに状態 JSON で送ります。

アプリは 2 つの `StreamServer`（5555 と 5556）を持ち、AppModel が全体を管理します。

### カメラを動かす条件

`(接続中 && streamActive) || 録画中 || iPhone 側のプレビューがオン` のときだけカメラを動かします。使っていないときに止めて、発熱とバッテリー消費を抑えます（[PROTOCOL.md の stream](PROTOCOL.md#stream（カメラを動かすタイミング）)）。

## Windows 側（PC）のパイプライン

ソースは `windows/` にあります。

1. **接続**（`phonecam_iphone.py`）: usbmux で iPhone を探して Connect する、または Wi-Fi で直接接続。切断されても、接続中の間は 2 秒ごとに自動で再接続します。
2. **受信・デコード**: メッセージを取り出し、PyAV（`av`）でデコード。ハードウェアデコード（Direct3D 11、`d3d11va`）が既定で、使えない／途中で失敗したときは自動でソフトウェアに切り替えます。
3. **出力**: サイズ変換・反転・「出力の形」「合わせ方」への収め込みをして、仮想カメラへ渡します。
4. **GUI**（`phonecam/qt/`、入口は `phonecam_qt.py`。旧 Tk 版は `phonecam/ui/`）: 接続・映像 / 画質調整 / エフェクト / 録画 / 音声 / 状態 / セットアップのタブ。設定は `%APPDATA%\PhoneCam\phonecam_settings.json`。
5. **セットアップ**（`phonecam_setup.py`）: 初回ウィザードとセットアップタブ。必要なソフトの確認・インストール、iPhone のセットアップ案内。

### スレッド構成

| スレッド | 仕事 |
|---|---|
| 接続スレッド（`phonecam-link`） | 接続、受信、デコード、pong など受信した内容の処理（返事はすぐに処理） |
| 出力スレッド | サイズ変換・反転・仮想カメラへの送信（受信スレッドから「最新の1枚」を受け取る） |
| ping スレッド（`phonecam-ping`） | 1 秒ごとに ping を送る |
| 音声チャンネル（`phonecam-audio-ch`） | 5556 の接続と受信、再生バッファへの投入 |
| GUI（メイン） | 画面の更新、設定、制御の送信 |

## 仮想カメラ

### 出力先

- **PhoneCam（専用カメラ）**: exe 版の既定。OBS の「仮想カメラ開始」と同時に使えます。使用中の自動検出ができるのはこの出力先だけです。
- **OBS Virtual Camera / Unity Capture**: 従来どおりの仮想カメラ（pyvirtualcam 経由）。OBS の「仮想カメラ開始」とは同時に使えません。使用中の検出ができないので、カメラは「接続中ずっと」と同じ動きになります。

### 専用カメラのしくみ

[softcam](https://github.com/tshino/softcam)（MIT）v1.8.1 を、GitHub Actions で表示名「PhoneCam」・独自の CLSID・独自の共有メモリ名に書き換えてビルドしています（他の softcam 利用アプリと衝突しません）。受信アプリは（exe 版では内蔵し `%ProgramData%\PhoneCam\softcam\<ハッシュ>\` に登録した）`softcam.dll` を ctypes で読み込み、BGR24 のフレームを渡します。CLSID は `windows/phonecam/core/softcam_reg.py` の `PHONECAM_CLSID` と `windows/softcam_ext/build-slots.ps1` で一致させてください。

exe 版では DLL を exe に内蔵し、登録時に `C:\ProgramData\PhoneCam\softcam` にコピーします。登録は「接続・映像」タブの「PhoneCamカメラ」欄（**登録する（更新）** / **登録を解除**）で行います。

### 仮想カメラのサイズを固定する理由

OBS は仮想カメラの最初のサイズを覚えるため、途中でサイズが変わると映像が止まります。そこで仮想カメラのサイズを iPhone の解像度から切り離して固定し（既定 1920×1080。1280×720 / 3840×2160 も選べます）、映像をその中に収めます。

- 出力の形: 向きの設定に合わせる（既定）/ 横長で固定 / 縦長で固定 / 映像のサイズそのまま（向きが変わると出力サイズも変わる）
- 合わせ方: 余白を付けて全体を表示（既定。余白は黒、背景「切り抜き(緑)」のときは緑）/ はみ出す部分を切り取って埋める
- 仮想カメラのサイズが変わるのは「出力サイズ」「出力の形」「向き」を変えたときだけです。そのときだけ、OBS はソースを一度非表示→表示、Discord はカメラを一度オフ→オンにする必要があります。

### 使用中の検出

softcam の共有メモリ（`PhoneCam/SharedMemory`）の先頭ヘッダ `{u32 image_offset, u16 width, u16 height, f32 framerate, u8 is_active, u8 connected_min_version, u8 sender_heartbeat, u8 receiver_heartbeat, u64 frame_counter}` のうち、`receiver_heartbeat`（15 byte 目）を受信アプリが読み取り専用で 0.5 秒ごとに見ます（共有メモリは作らず、開くだけ）。softcam を使うアプリ側が約 20ms ごとに +1 するので、3 秒以内に値が変わっていれば「使われている」と判定します（8bit で一周するので、前回値との不一致だけを見ます）。送る側（受信アプリ）の `sender_heartbeat` も映像の有無と無関係に動くため、映像が止まっていても使う側は繋がったままです。補助として `connected_min_version` が 0 から 0 以外になった（アプリが新しく開いた）ことも「使われた」とみなします。「状態」タブの「使用中の検出」に判定結果（使用中 / 未使用 / 共有メモリなし）と、共有メモリのサイズ・アプリの接続履歴を表示します。

softcam の使う側（DirectShow フィルター）は、作られた時点の幅・高さを覚え、**同じ幅・高さで有効な共有メモリがあるときだけ**映像を受け取ります（違うと映像は黒のまま、`receiver_heartbeat` も動きません）。また、フィルターが作られたときに共有メモリが無いと、そのフィルターは映像を受け取れません。そのため、受信アプリは次のようにしています。

1. 起動時に（接続前でも）待機用の黒い映像で専用カメラを作る
2. 仮想カメラのサイズを iPhone の解像度から切り離して固定する
3. カメラを作り直すときは共有メモリの監視をいったん手放す（開いたままだと softcam が同じ名前で作り直せないため）

### カメラの自動起動

「iPhoneのカメラの動作」が「使われているときだけ（自動）」のとき、上の使用中の検出で OBS・Discord などが専用カメラを開いている間だけ `stream` を有効にします（使われなくなって「止めない / 10秒 / 30秒 / 1分 / 5分」のあとで停止。既定は 1 分。止まったあとも監視は続けるので、アプリがカメラを開き直すと自動で再開します。手動の「一時停止」だけは、アプリが開き直すまで再開しません）。「使われている」の判定に最大 3 秒ほど、カメラ起動に 1〜2 秒ほどかかります。受信アプリを開いている間は、PhoneCam カメラ（黒い画面）を常に用意しておくので、iPhone のカメラが止まっていてもカメラ一覧に「PhoneCam」が出て、選ぶとカメラが動き始めます。

## 音声の経路

```
iPhone マイク → (約5msごとのパケット) → ポート5556 → 再生バッファ → WASAPI → CABLE Input ⇒ VB-CABLE ⇒ CABLE Output → OBS / Discord
```

- 音声は専用の通信路（5556）で受け取ります。古い iPhone アプリなどで専用の通信路が無いときは、自動で映像と同じ通信路（5555）に戻ります（「映像と共用」と表示）。
- **再生バッファ**は、音が届く間隔の揺れ（ジッター）を測って自動で調整します（＋「音声の遅延」で足した分）。途切れる場合は自動で少し増え、安定していれば小さくなります。下限は設定で変わります。
  - **低遅延優先**（既定）: パケットが小さく安定しているとき（到着間隔 10ms 以下。iPhone の低遅延マイク経路は約 5ms）は下限 8ms。大きいパケットのときは max(15ms, 2.5×ジッター)。
  - **安定優先**: 下限 20ms。
  - 溜まりすぎたとき（目標を max(20ms, 3×目標) 超えたとき）は古い方を捨てて目標に戻します。足りなくなったときは無音を出し、「アンダーラン回数」に数えます。
- **排他モード**: WASAPI 排他モードで出力先を開き、Windows のミキサーを通さずに 5ms ブロックで再生します。出力先が「CABLE Input」のときは最初からオン、それ以外はオフ。排他で開けないとき（他のアプリが使用中、形式が合わない、古い sounddevice など）は自動で共有モードに切り替えます。48000 Hz → デバイス既定の順に、16bit → 32bit → float で試します。
- **音声の遅延表示**は「iPhone で録音してから、PC の再生バッファを出るまで」の平均で、VB-CABLE 内部の遅延は含みません。
- VB-CABLE 自体にも大きな内部バッファ（コントロールパネルの「Max Latency」。初期値は大きめで、48kHz で 100ms 以上になることがあります）があります。「VB-CABLEの遅延設定を開く」ボタンで `VBCABLE_ControlPanel.exe`（管理者として）を開き、512〜7168 サンプルの範囲で下げられます。
- VB-CABLE のインストーラーは Windows の「既定の音の出力先」を CABLE に切り替えてしまうことがあります。PhoneCam は入れる前に現在の既定デバイスを控え、入れたあと（約 20 秒間と、次の 2 回の起動時）に CABLE へ切り替わっていたら元に戻します。PhoneCam の受信アプリだけが「CABLE Input」へ音を出します。

## 遅延の設計

目標は、USB 接続・1080p60 で **おおよそ 50〜100ms** です（理論上の目標値で、環境により変わります）。

- iPhone: 手ブレ補正オフ、遅れたフレームは破棄、低遅延レート制御、B フレームなし
- 通信: TCP_NODELAY、送信が詰まったときはキーフレーム以外を破棄、未送信の映像は最大 1 フレーム
- PC: 受信・デコードのスレッドと、仮想カメラへ出力するスレッドを分け、出力が遅れても受信が止まらないようにしています（次の節）
- 音声: 映像とは別の通信路（5556）で、映像の渋滞に巻き込まれないようにする

### 映像を溜めない工夫

以前は、1 つのスレッドが「受信 → デコード → サイズ変換 → 仮想カメラへ出力」を順番に行っていました。4K のようにこの処理がフレーム間隔より長くかかると、受信できなかった映像が OS の受信バッファに溜まり、USB 自体は 1〜2ms でも「通信」が 100ms 以上、往復(RTT)が 300ms 前後に見えていました（音声も ping の返事も、溜まった映像のうしろで待たされます）。

- 受信スレッドは受信とデコードだけを行い、デコードしたフレームは出力スレッドへ「最新の 1 枚」として渡します（出力が間に合わなければ古いフレームを上書きして捨てます）。サイズ変換・反転・仮想カメラへの送信は出力スレッドが行います。
- デコード自体が追いつかないとき（デコードが映像の間隔より遅い状態が積み上がる、または通信側の遅れが 100ms を超える）は、**次のキーフレームまで非キーフレームのデコードを省略**して追いつき、キーフレームを要求します（要求は 1 秒に 1 回まで）。このとき状態タブに「PCの処理が追いつかないためフレームを間引いています」と間引いたコマ数が出ます。
- 受信バッファ（SO_RCVBUF）を 512KB に制限しています。PC が遅れたときは、OS の大きなバッファではなく iPhone 側の送信キューで古い映像が捨てられるので、遅れが溜まりません。TCP_NODELAY も有効です。
- ping の返事は受信スレッドですぐに処理するので、映像が溜まらなければ RTT は数 ms になります。

### コーデックと遅延

遅延は H.264 も HEVC もほぼ同じです（v1.4 以降）。以前は「HEVC のほうが遅延が小さい」ことがありましたが、これは PC の処理が追いつかず映像が溜まっていたためで、サイズの小さい HEVC のほうが溜まりにくかっただけです。今は溜まらないようにしているので、違いは通信量とデコード負荷だけです。

### 遅延の計測

状態タブでは、1 秒ごとの ping で iPhone と PC の時計のずれと往復時間(RTT)を推定し、映像 1 枚ごとに **iPhone処理 / 通信 / PC処理 / 合計** を出します（直近約 60 フレームの平均）。計算式は [PROTOCOL.md](PROTOCOL.md#遅延の計算) を見てください。カメラの露光や OBS の表示までの時間は含みません。含めた実際の遅延は、画面の「計測用タイマーを開く」を使って、カメラをタイマーに向け、OBS のプレビューに映るタイマーと実物のタイマーを一緒にスクリーンショットして、2 つの差で測ります。
